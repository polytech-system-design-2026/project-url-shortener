# Этап 3. Масштабирование

## Цель

Убрать PostgreSQL с горячего пути: редирект обслуживается из кэша в Redis, а подсчёт переходов уходит в асинхронную очередь. Измерить эффект нагрузочным тестом.

## Что нужно сделать

1. **Сначала снимите базовые числа — до любых изменений.** На коде этапа 2 заполните `loadtest/locustfile.py` (сценарий — в разделе «Нагрузочный тест» ниже), поднимите сервис и запустите:

   ```bash
   make up
   make loadtest
   ```

   Сохраните итоговую таблицу locust: это колонка «до» в отчёте.
2. Обновите `develop` после merge этапа 2 и поднимите этап:

   ```toml
   [tool.course]
   stage = "3_scaling"
   ```

3. Добавьте в `docker-compose.yml` сервис `redis` с `healthcheck`, порт наружу не публикуется. `app` стартует после готовности `redis`.
4. **Кэш редиректов.** `GET /{code}` сначала ищет URL в Redis; при промахе читает из PostgreSQL и кладёт в кэш. Ссылки не меняются, поэтому TTL не обязателен. Переход по ссылке, которую уже открывали, должен работать при остановленном PostgreSQL.
5. **Подсчёт переходов через очередь.** `GET /{code}` не пишет в PostgreSQL, а кладёт событие перехода в очередь в Redis — Streams, list или библиотека, на ваш выбор. Отдельный обработчик (воркер) читает очередь и увеличивает счётчик в БД. Варианты:
   - сервис `worker` в compose из того же образа, с другой командой — например, `python -m app.worker`;
   - фоновая задача внутри `app`. Тогда в `ARCHITECTURE.md` объясните, почему так.
6. Добавьте столбец для счётчика **новой миграцией** — первую не редактируйте, она уже применена.
7. Реализуйте `GET /links/{code}/stats` и добавьте его в `docs/openapi.yaml`.
8. `/health` проверяет и PostgreSQL, и Redis.
9. Не меньше 3 новых своих тестов.
10. Повторите нагрузочный тест с теми же параметрами и заполните раздел README «Нагрузочный тест».
11. Допишите в `docs/ARCHITECTURE.md` раздел `## Что изменилось на этапе 3`: что уехало в Redis, как устроен воркер, что происходит с событиями, если воркер упал.

## Контракт

| Метод | Путь | Ответ | Коды |
|---|---|---|---|
| GET | `/links/{code}/stats` | `{"code": "Ab3dE9", "clicks": 12}` | 200; 404 |

- У новой ссылки `clicks` = 0.
- После N переходов `clicks` = N не позднее чем через 5 секунд.
- Если PostgreSQL остановлен, `GET /{code}` по уже открытой ссылке — по-прежнему 307. `POST /links` в это время может отвечать 503, это не проверяется.
- Весь контракт этапа 2 продолжает действовать.

Что проверяет CI (`contract_tests/stage_3/`, плюс все тесты `stage_2/`):

- статистика новой ссылки и 404 для неизвестной;
- 7 переходов → `clicks` = 7 не позднее чем через 5 секунд;
- ссылку открыли → `docker compose stop db` → `GET /{code}` по-прежнему 307 → `docker compose start db`. Тест сам возвращает БД в исходное состояние.

## Критерии приёмки

- CI зелёный.
- Редирект действительно читает из Redis: при попадании в кэш запроса в PostgreSQL нет.
- Воркер подтверждает обработку события после записи в БД — или в README честно сказано, что при падении воркера события теряются.
- Раздел README «Нагрузочный тест» с параметрами, таблицей и выводами.
- Счётчик добавлен новой миграцией.
- Не меньше 3 новых своих тестов.
- В `ARCHITECTURE.md` есть раздел «Что изменилось на этапе 3».

## Типичные ошибки

- **Кэш есть, но горячий путь всё равно ходит в БД** — например, сначала проверяется существование ссылки в PostgreSQL, а потом берётся URL из кэша. Тест с остановленной БД это поймает.
- **Воркер забирает событие и не подтверждает обработку.** С Redis Streams без `XACK` события копятся в списке ожидающих; со списком и `LPOP` событие теряется, если воркер упал между чтением и записью в БД.
- **Воркер не запущен.** `docker compose ps` — есть ли `worker` и не перезапускается ли он в цикле; `docker compose logs worker`.
- **`/health` не проверяет Redis.** Тогда CI начинает тесты, пока Redis ещё не готов.
- **Тест с остановленной БД падает на ожидании `/health`.** При остановленном PostgreSQL `/health` честно отвечает 503 — это правильно, тест ходит не в `/health`, а в `/{code}`. Падение значит, что `/{code}` не отвечает 307.
- **Старая миграция отредактирована вместо новой.** На уже поднятой базе alembic её не применит: версия считается выполненной.
- **Разные параметры нагрузки «до» и «после»** — сравнение теряет смысл.
